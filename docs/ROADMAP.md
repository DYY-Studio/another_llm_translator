# 产品路线图

本文记录尚未实现的方向、已实现实验的后续进入条件及其判断依据。已经实现的行为和验收要求见
[`MINIMAL.md`](MINIMAL.md)；历史实施过程可从 Git 记录中检索。

后续工作继续遵循以下边界：

- 项目目录仍是完整项目边界，不引入 Repository 层或双写路径。
- 不自动判断 Provider，不静默 fallback，也不提供任意格式互转。
- 新能力必须由真实需求和可测试规则驱动，不提前建设通用框架。
- 已发布的 SQLite 项目、Preset 和 Adapter schema 如需变更，必须提供明确迁移或主版本边界。

## 优先方向

### Windows Tauri 公开 Beta

- 完成 Windows sidecar、Credential Manager、安装包签名、Unicode 和长路径验收。
- 验证外部项目、卸载后保留用户数据以及安装和升级流程。
- 只有开启局域网共享时才请求必要的防火墙权限。
- 继续采用手动升级，不引入 Windows 专属业务分支。

### Linux Tauri Beta

- 确定目标发行版、安装包形式，以及 Wayland 和 X11 的支持范围。
- 验证 sidecar、Secret Service、项目路径、文件权限和局域网共享。
- 缺少可用 Secret Service 时，明确失败或要求使用 `environment` 凭据，不保存明文密钥。
- 不承诺未经测试的发行版或桌面环境。

### Labs

#### 当前实验：术语页中的内容概括

“内容概括 · 实验”已经作为术语页子页提供，用来验证“术语扫描同时产出片段概括，
再由用户手动聚合完整概括”的可行性。它面向需要快速了解文档内容的读者，也帮助译者
在术语页内回看片段上下文；实验结果不构成稳定的摘要质量承诺。

- 概括按通用 `(file_id, part_id)` 边界工作，使用同一套 Document Adapter 边界，不识别
  章节，不为 TXT、EPUB 或外部格式增加专用路径。
- 概括参与选择保存在项目中，但只影响概括生成；术语扫描仍覆盖整个项目。标准术语入口、
  CLI 和 `run-all` 不自动加入概括。
- 联合请求先返回一条 `summary`，随后返回 `term`，最后返回 `end`；术语来源仍是原文。
  已有术语完成而只缺概括时，入口仅执行 `summary-only` 回填，不重复扫描或发布术语。
- 片段结果必须由用户显式选择参与边界后聚合，完整聚合沿用当前已保存的参与选择。
  唯一片段已覆盖整个边界时直接采用；多个片段按原文顺序聚合，超长输入递归压缩并
  保留原文引用。
- 结果和源文范围保存在 SQLite；源文变更、响应失败、取消和恢复均保留可用历史并明确
  显示状态。Markdown 导出使用独立选择，可包含已完成的历史结果。
- 概括页支持项目级全选/取消全选、筛选范围选择和按 File 的半选状态；切换阶段后返回时
  保留子页、筛选、边界、页签和滚动状态。

外部 Document Adapter 只需提供通用 File/part/Segment 契约即可参与实验。若 Adapter 的
`model_source` 无法安全拆分并保留原文定位，系统会明确失败，不猜测字符映射。实验质量
 使用代表性材料的人工检查清单和示例输出，不设随机百分比门槛。

#### 后续方向与复用边界

独立 Labs 工作区和章节识别仍是远期方向，当前不为它们预留入口、章节编辑器、工具注册
框架或通用工作流。若后续需要把内容概括移入独立辅助区，先根据实际使用反馈重新评估入口
和数据边界；现有术语子页行为保持可追溯。

| 方向 | 进入条件 | 核心验证 |
|---|---|---|
| 多角度评价 | 章节定位和原文追溯经过验证，并选定具体评价角度 | 观点有原文依据，不能默认摘要足以支撑所有评价 |
| Ruby 注音 | 明确日语阅读需求与代表性样本后，可独立推进 | 正文保真、注音位置、专名和歧义读音、已有注音处理 |
| 用户组合 Pipeline | 多种能力长期稳定，且出现反复使用的真实组合需求 | 先判断固定组合是否足够，再讨论可编排 |

复用已有模型调用、Preset、凭据、限流、取消、诊断和有界并发能力。分块、上下文及成果模型按用途设计，出现至少两个真实用例后再提炼共享实现。

当前实验的接口、配置和内容概括记录已按实现文档落地；后续章节范围确认或独立工作区若成为真实需求，另行设计，不强行套用逐 Segment 文本回写接口。

#### 推进节点与验证

1. **实验观察**：用代表性材料检查片段覆盖、完整聚合、原文引用和失败恢复。
2. **独立入口评估**：只有出现稳定的独立辅助工具需求后，才评估 Labs 工作区和章节范围确认。
3. **后续工具**：依据使用反馈，分别立项注音或首个评价功能。

当前实验对外使用前，验证覆盖边界遗漏、响应失败、源文变化、原文引用，以及恢复时的
重复或遗漏；质量由人工检查清单评估，界面变更通过浏览器和截图验证。

自动化使用模拟模型响应，概括质量使用代表性材料人工评估。界面变更通过浏览器和截图验证，合并前执行规定的完整测试。

每个节点进行减法审查，不为超远期 Pipeline 预留框架。涉及已有项目结构变化时，先确认真实数据与兼容需求，再决定迁移方式；当前实验的实施计划和验证记录以 Git 与实现文档为准。

## 协议成熟度

产品功能和协议稳定性分别推进。功能可用不代表 SDK 已冻结。

### 声明式 JSON LLM Adapter

schema 2 已覆盖类型化占位符、嵌套 body、自定义认证 Header、响应 JSON Pointer
负索引、消息形状转换和 SSE。HTTP、限速、重试、取消、Run 收尾和调试记录仍由宿主管理。

后续只在现有声明能力无法表达真实端点时扩展 schema。API Key 不得进入 URL、请求正文、
Run 快照或阶段指纹。

### Document Adapter 与可信 Python 插件（Beta）

继续补充以下真实样本验证：

- EPUB spine、命名空间、导航、CSS、图片、字体和跨节点文本；
- SRT 核心语法边界及模型对样式标记的处理；
- 外部 Document Adapter 的版本升级和运行时安装需求。

只有出现第二个真实且持续维护的外部 Document Adapter 后，才决定兼容范围和运行时安装策略。
Translation Validator 保持窄接口，只接收源文、候选译文和宿主确定的逐 Segment 术语命中；
不建立通用 DOM 或自由 HTML 协议。

### Python LLM Adapter（provisional）

只有出现声明式 JSON POST 无法表达的真实端点后，才设计首个 Python LLM Adapter。
在两个真实实现共同验证前，不提供动态加载器或兼容承诺。

### 稳定门槛

每类协议必须独立满足以下条件，才能标记为稳定：

- 至少两个真实且持续维护的实现；
- 统一契约测试和端到端测试通过；
- 配置变化、指纹、恢复、插件缺失和版本升级行为明确；
- 协议版本范围、兼容政策和废弃周期已经记录。

Document Adapter 需要 TXT、EPUB 和至少一个外部插件稳定后才能冻结。Python LLM Adapter
必须等待 OpenAI-compatible JSON Adapter 之外的真实特殊协议。

## 明确不规划

当前不建设远程插件、多语言进程协议、在线市场、自动安装、插件沙箱、自动 Provider 判断、
静默 fallback、通用 DOM、排版树或工作流引擎。桌面端不另建业务后端，也不改用 Electron。

应用不面向公网部署。公开 Beta 前不建设自动更新、TLS 证书、多账号权限或远程遥测。
超大列表不自制虚拟滚动算法；SQLite 不引入 ORM；未经过真实剖析，不加入 `orjson` 或
`lxml`。
